# kiosk (#35) — per-device wizard progress (§2★ב), 11/08/2026

`setupsteps.js` landed the checklist and stores nothing by design. This step is
the state it deliberately left out: **which boxes are ticked, per device**.

Why it has to be storage and not page state — §2★ב's flow runs across two people
and a reboot. The owner opens the wizard in the console; an installer stands at
the tablet with a cable. Between them the list includes removing every account
(often a factory reset) and an `אתחלו את המכשיר`. Progress held in the page dies
on the reload that the checklist itself asks for, and the second person opens an
empty list on a job half done.

## Decisions the tests pin down

- **Presence of a row is a tick; unticking deletes it.** A boolean column would
  keep a row for every box ever *looked at*, and "unticked" and "never reached"
  are the same state to the wizard — there is nothing for the second value to
  mean.
- **One box per request, not a whole-set `PUT`.** This is the opposite of
  `PUT /devices/:id/clients`, and deliberately: that is one owner sending a
  configuration complete, this is two people ticking a shared list at the same
  time. A whole-set save has whichever tab loaded first wipe the other's ticks —
  the failure being progress running *backwards* while someone watches it.
  Both directions are `INSERT OR IGNORE` / `DELETE`, so a double tap on a tablet
  and a retry over a hall's wifi are not errors the wizard has to explain.
- **Ids are validated against every id the checklist can ever produce**, computed
  from `setupChecklist` over both tracks × with/without a code rather than
  written out — a list written out here silently stops covering a step somebody
  adds there, and a missing id is a checkbox that does nothing. It is validated
  against that union and **not** against the list the caller is looking at: the
  visible list varies (`create-code` disappears the moment a code exists,
  possibly generated by the other person in another tab), so validating against
  the current view would refuse a tick that was legitimate a second earlier.
  Contextual filtering already happens on the way out, in `checklistProgress`.
- **A tick for a step that is no longer on the list is kept, and does not
  count.** `create-code` ticked, then a code appears: the row stays (the code can
  expire and the step comes back with its tick intact) but `checklistProgress`
  drops it, or the wizard shows 12/11 and a completed banner over an unfinished
  install.
- **An unknown step id is a 400, not a silent drop.** The wizard renders its own
  list, so a step the server won't store is a checkbox that appears to work and
  loses the tick on the next load.
- **Switching track keeps the ticks.** The two tracks are one list with a flag —
  they differ in the wording of three steps, not in which steps exist — so a step
  done on one is done on the other. Clearing would punish the person who
  discovers half way down that the tablet has no Play Store, which is the moment
  the switch exists for.
- **NULL `setup_track` resolves to `generic`, and the column has no default.**
  `generic` assumes neither a Play Store nor a Google account, so it is merely
  less specific on a GMS device; defaulting to `gms` would send whoever opens the
  wizard on an existing device hunting for menus their tablet does not have.
- **`ticked_by` is `ON DELETE SET NULL`.** Who ticked it is the useful question
  when an install stalls across two people; losing the tick because a staff
  account was closed would mean the install goes backwards. Observable only for a
  ticker who is *not* the device's owner — `devices.owner_id` cascades — which is
  the admin case the console already allows, and the replay drives it that way.
- **`setup_track` was added to `CONSOLE_DEVICE_FIELDS`.** `devicepayload.js` is
  an allow-list precisely so a new `devices` column fails a test until someone
  decides; `devicepayload.test.mjs`'s DDL copy and its `dropped` assertion were
  updated in the same change, so the reviewed set is still exactly
  `['device_token']`.

## Not done here

- **No screen.** The wizard UI (§2★ב's checkbox list) is the next step; nothing
  in `public/` calls these routes yet, so the four endpoints are reachable only
  by hand.

  comes from the tablet rather than from a console session, but no agent route
  writes one.
