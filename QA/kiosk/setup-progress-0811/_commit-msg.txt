Added device_setup_steps, devices.setup_track, src/setupprogress.js and four
routes under /api/devices/:id/setup.

Presence of a row is a tick; unticking deletes it. A boolean column keeps a row
for every box ever looked at, and unticked and never-reached are the same state
to the wizard — there is nothing for a second value to mean.

One box per request, not a whole-set PUT — the opposite of /devices/:id/clients
and deliberately so. That is one owner sending a configuration complete; this is
two people ticking a shared list at once, where a whole-set save has whichever
tab loaded first wipe the other's ticks, and progress runs backwards while
someone is watching it. Both directions are idempotent: a double tap on a tablet
and a retry over a hall's wifi are not errors the wizard has to explain.

Ids are validated against every id the checklist can ever produce, computed from
setupChecklist over both tracks and both code states rather than written out — a
written list stops covering a step somebody adds there, and a missing id is a
checkbox that does nothing. Not against the caller's current view: create-code
vanishes the moment a code exists, possibly generated by the other person in
another tab, and a tick legitimate a second earlier must not be refused. A tick
for a step no longer listed is kept and does not count — the code can expire and
the step comes back with its tick intact, and counting it shows 12/11 and a
completed banner over an unfinished install. An unknown id is a 400 rather than
a silent drop: the wizard renders its own list, so a step the server will not
store is a checkbox that appears to work and loses the tick on the next load.

Switching track keeps the ticks. The tracks differ in the wording of three steps
and in nothing else, and the switch is what someone does on discovering the
tablet in their hands has no Play Store — after already doing some of it.

setup_track has no default; NULL resolves to generic, which assumes neither a
Play Store nor an account. Defaulting to gms would send whoever opens the wizard
on an existing device hunting menus their tablet does not have.

setup_track also went into CONSOLE_DEVICE_FIELDS. That allow-list exists so a new
devices column fails a test until someone decides, so the DDL copy and the
dropped assertion in devicepayload.test.mjs moved with it — reviewed exclusions
are still exactly ['device_token'].

QA/kiosk/setup-progress-0811: 12 unit cases, 106/107 across the suite
(routing.test.mjs imports express and still cannot run here; 94/95 before, so the
12 are the whole difference), plus a 13-assertion replay of the boot migration
against node:sqlite on a database shaped like the live volume — both existing
rows keep every value, the new column is NULL on both, and a second boot adds
nothing and loses nothing.

Not deployed, and no screen: nothing in public/ calls these routes yet.
