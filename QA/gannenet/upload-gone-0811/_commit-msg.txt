gannenet (40): a deleted file kept living in the teacher's own browser

The previous step ended on "a copy already in a teacher's browser or
service-worker cache survives the delete -- nothing server-side can reach it."
Half of that is untrue. The copy on her disk is unreachable; the copy in her
service worker is not, because this app writes the service worker.

Two things stood in the way. Files are cache-first in FILES with no expiry and
no revalidation -- correct for Drive files and the 258 seed assets, which are
immutable, and wrong for the one source that can now be deleted. And nothing on
the client could have acted on it anyway: /api/upload/[name] collapsed every
non-ok upstream into 502, so a deleted file and a broken one were the same
answer, and a service worker may not drop a teacher's offline material on a
maybe.

The route now returns a real 404 for gone, keeps 502 for broken, and exports a
HEAD handler so the check moves no bytes. evictIfGone() runs behind the response
for /api/upload/ only and deletes with ignoreSearch, since ?dl=1 and the bare
URL are two cache keys for one file.

Verified on the production build against the real bucket: a real upload cached
under both keys, deleted through the real /api/admin/delete, then viewed again
-- the view is still served 200 29278B from the cache, both keys are gone after
it, and the next view is 404 with nothing put back. Offline, with the server
stopped, the same file is served from FILES and is still cached three seconds
later: a rejected check is not "gone".

Three defects the verification itself found, all fixed here. The obvious HEAD --
reuse the GET upstream and body.cancel() it -- hangs, answering 400 and 404 fine
and never returning even a status line for the one id with bytes behind it. Then
Storage's CDN and its origin disagreed about whether the file exists: seconds
after the delete an upstream HEAD said gone while an upstream GET returned 200
and all 29,278 bytes, so the route called a deleted file broken and served its
bytes. And with the eviction finally working, the browser undid it -- the file's
own max-age=86400 let the HTTP cache re-serve the deleted bytes and cacheFirst
put them straight back.
