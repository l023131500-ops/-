gannenet (40): the save that looked atomic, and the fix for it that also wasn't

The previous step left one open line: setOverride() is a read-modify-write with
no compare-and-set. Measured first, two concurrent saves of two different files
against the real bucket: a save was lost in 4 of 4 runs, and both calls returned
ok. The whole override map lived in one overrides.json, so every save rewrote
shared state.

Both ways to close that were probed rather than assumed, and both are dead:
If-Match is accepted and IGNORED on upload (a deliberately bogus ETag still
returned 200 and still overwrote), and a lock object cannot be released, because
the anon key may create and overwrite but not delete -- create-if-absent on an
existing key is a real atomic 409 KeyAlreadyExists, DELETE is 403 AccessDenied.

Write-then-verify was then implemented, measured, and thrown away: still 4 of 4
lost. Re-reading after the write proves nothing, because "it landed" is only
true at the instant of the check -- one writer verified its own entry, returned
ok, and a concurrent write clobbered it a moment later. It is written up in
STATUS.md because it looks correct and the next reader would try it.

What ships removes the shared write instead of guarding it: one object per file,
overrides/<fileId>.json. Two files are two keys and cannot collide; two saves of
the same file are last-writer-wins on one field, which is what a human expects.
Same race, same harness: 0 of 4 lost. Clearing an override writes {} instead of
deleting, since anon cannot delete, and readers treat an empty entry as absent.
readOverrides() folds the legacy overrides.json in underneath the per-file
objects, which stay authoritative, so a bucket written by the old code keeps its
curation.
