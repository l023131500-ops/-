31 gesher: the partner's one business action wrote to the one column he may not write

The previous step shipped /gesher/partner/clients with a "treatment status" dropdown —
the only business action a partner has there. Reading the schema on the way to building
the last placeholder screen showed why partner_feedback_notes was described as "already in
the table": it is the ONLY column `authenticated` may write on partner_assignments.
Migration 20260605003212 does REVOKE UPDATE ... GRANT UPDATE (partner_feedback_notes),
and no later migration gives treatment_status back.

The handler wrote it through the CALLER's client. Postgres checks column privileges before
RLS, so this never depended on which row was picked. Measured against production, signed in
as the §1ב test user, with an id matching no row:

  treatment_status         HTTP 403  42501 permission denied for table partner_assignments
  partner_feedback_notes   HTTP 204  allowed

Every partner touching that dropdown got a permission error in the toast. The same trap was
avoided on `tasks` — migration 20260610113503 granted UPDATE (status, priority, updated_at),
and the tasks board is fine. partner_assignments simply never got its GRANT back.

The revoke is deliberate: it stops a partner moving his own row through the funnel by hand,
and stops him rewriting partner_id past the USING-only policy. So no GRANT was restored.
Instead the ownership check stays with the caller ("Partners read own assignments" narrows
it, so a foreign id and a missing id both answer Forbidden) and the one legitimate transition
is made as service_role, on the single column, after that check.
