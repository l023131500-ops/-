The sweep found a second open door, and this one returns data rather than
creating an account.

GET functions/v1/api/teachers, /seekers and /contacts each answer 200 with no
apikey header and no Authorization header at all. The function runs with
SUPABASE_SERVICE_ROLE_KEY and verify_jwt=false, so RLS does not apply to it,
and each of the three returns a full select("*") over a lead table: name,
phone, email, city and free-text notes for every person who ever filled in a
form, used the chatbot or called the IVR line.

Nothing has actually leaked. The tables are empty - /stats returns 0/0/0 - so
the measurement is of an open route, not of a disclosure. Every lead collected
from now on would have been public.

This was not deliberate exposure. The three routes are documented only inside
the admin panel, and the app does not call them at all: AdminDashboard and
MatchingTab read the lead tables through PostgREST under the user's session.
Gating them breaks no caller, which is why the fix is a gate and not a
redesign.

requireAdmin() now runs before all three: read Authorization: Bearer <user
jwt>, auth.getUser(token), then has_role(uid,'admin'). 401 with no token or a
token that is not a user, 403 without the role, and 403 if the role check
itself errors - it fails closed. The public reads (lessons, lesson/:id,
search, stats, cities, subjects) and all four POST submission routes stay open;
that is the product. verify_jwt alone would not have closed this, for the same
reason as #160: the anon key is a valid JWT and ships in every page load.

The gate is verified live at the two inputs it decides on, against the real
project. The anon key presented as a user token is refused by GoTrue with 403
bad_jwt "missing sub claim", so auth.getUser errors and the caller gets 401. A
genuinely signed-in customer (test@more30.com) is accepted as a user and then
has_role(sub,'admin') returns False, so that caller gets 403. That is evidence
about the decision inputs, not about the deployed function - see below.
