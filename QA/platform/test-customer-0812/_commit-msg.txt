written into core.secrets and never turned into an account.

Created it the way a visitor creates one -- the public signup endpoint with the
same anon key each site already ships to the browser, never a service key -- on
all nine Supabase projects the live systems authenticate against. 08 is
protected and is deliberately absent from the list.

Eight of the nine now sign in with the documented password. That is also the
§1א check ("register -> log out -> log in with the same details") on eight
projects at once: the hub answered 200 immediately, and a wrong password on the
same account is refused, so register and login are not disagreeing about the
hash there.

The eight needed their mail confirmed, and this is the part worth carrying:
test@more30.com is a real mailbox routed to Resend. The seven confirmation mails
were readable from here, and opening each verify link confirmed the account --
no console, no webmail, nothing waiting on the user. Two of the redirect targets
answer 418 (NetFree blocks *.lovable.app), but the token in the redirect proves
the verification already happened server-side.

answered user_already_exists, so the account was created in an earlier run and

NEEDS_USER as 0ש with both exits: the next run re-reads the inbox, and only if
it is still empty does it need the user's Supabase console.
