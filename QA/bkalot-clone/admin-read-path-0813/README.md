# שכפול בקלות שכבה 2 — נתיב הקריאה (13/08/2026, migration 0060)

שכבה 1 נסגרה עם `more30.com/bkalot-studio` חי: פנייה נכנסת למסד מקצה לקצה.
מה שלא היה קיים הוא הכיוון ההפוך — **אין ולו שאילתה אחת שאפשר לקרוא בה פנייה
בחזרה**. `bkalot_clone` אינה חשופה ל-PostgREST כלל (נמדד ב-0058), ולכן "רשימת
פניות" אינה שאלה של הרשאות אלא של פונקציה ב-`public`, בדיוק כמו הקליטה.

## מה נבנה

| פונקציה | מחזירה |
|---|---|
| `public.bkalot_clone_admin_cases(jsonb)` | רשימה מסוננת (`status`/`kind`/`q`) ומדופדפת (`limit`/`offset`) + `total` |
| `public.bkalot_clone_admin_case(bigint)` | פנייה בודדת + איש קשר + הזכויות שלה + מטא-דאטה של מסמכים |

`SECURITY DEFINER`, `search_path` ריק, כל שם מלא, `EXECUTE` ל-`service_role` בלבד.

## המלכודת שהצעד הזה נבנה סביבה — ונמדדה, לא הונחה

`cases_contact_id_fkey` הוא `ON DELETE SET NULL`. מחיקת איש קשר **מייתמת פנייה
בשקט**, ו-JOIN רגיל היה משמיט אותה מהרשימה — פנייה שקיימת ואינה מוצגת נראית
בדיוק כמו רשימה תקינה. נבדק בפועל: איש הקשר של פנייה 13 נמחק, `contact_id`
הפך ל-`null`, והפנייה **עדיין מופיעה** ברשימה עם `contact: null` מפורש —
וגם במסך הפנייה הבודדת.

**סדר הרשימה נבדק ולא הונח:** שתי פניות הבדיקה נכתבו באותה פקודה ולכן
`created_at` שלהן זהה לחלוטין. בלי שובר-שוויון על `id` הסדר היה תלוי בתוכנית
הריצה — `order by created_at desc, id desc` בשני המקומות (גם בתת-השאילתה וגם
ב-`jsonb_agg`), אחרת הדפדוף היה יכול להחזיר את אותה שורה פעמיים.
