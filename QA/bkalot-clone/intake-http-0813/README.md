# bkalot-clone: לפנייה יש עכשיו נתיב HTTP — נמדד מקצה לקצה (core.issues #223, סעיף 1)

**מה היה.** מיגרציה 0058 יצרה את `public.bkalot_clone_intake(jsonb)` ונשללה ממנה EXECUTE
מכל מי שאינו `service_role` — `anon` ו-`authenticated` נמדדו `false`. כלומר שכבה 1 החזיקה
לוגיקת קליטה מלאה שאי אפשר היה לקרוא לה מדפדפן ולו פעם אחת. הפער נסגר כאן ב-edge function
אחת: `supabase/functions/bkalot-clone-intake/index.ts`, נפרסה כ-`bkalot-clone-intake`
version 1, `verify_jwt: true`.

היא דקה בכוונה. כל האימות, הכיווץ לפי הסוג וחיבור הזכויות נשארים במסד — ה-edge function
בודקת רק את מה שהמסד אינו יכול לבדוק (שיטה, גודל גוף, JSON תקין) ואז מעבירה. כך אין עותק
שני של הכללים שיכול להסתעף מהראשון.

## מה נמדד, על הכתובת החיה ולא על קובץ

`POST https://uhnrgujbdxhhmoxcjria.supabase.co/functions/v1/bkalot-clone-intake`
(`QA/bkalot-clone/intake-http-0813/probe.ps1`, פלט מלא ב-`probe-out.txt`).

| | בקשה | HTTP | גוף |
|---|---|---|---|
| A | OPTIONS **בלי** Authorization | **204** | — |
| B | POST בלי מפתח | **401** | `UNAUTHORIZED_NO_AUTH_HEADER` |
| C | GET עם anon | 405 | `method_not_allowed` |
| D | גוף שאינו JSON | 400 | `body_not_json` |
| E | גוף שהוא מערך | 400 | `body_not_object` |
| F | `kind` שהמסד דוחה | 200 | `ok:false, kind_invalid, allowed[3]` |
| G | גוף מעל 16KB | 413 | `body_too_large` |
| H | treatment מלא | 200 | `ok:true, case_id, rights_linked:59, queued:false` |
| I | info ששלח שדות של treatment | 200 | `ok:true, dropped:[situation,topic_no,documents]` |

**A ו-B הן העיקר, והן היו ההימור של הצעד.** `verify_jwt: true` דוחה כל בקשה בלי כותרת
Authorization — ואת ה-preflight הדפדפן שולח בלי כותרות. לו ה-gateway היה אוכף JWT גם על
OPTIONS, הטופס היה נחסם בדפדפן לפני שהבקשה האמיתית נשלחת, וכל בדיקה משורת פקודה הייתה
עוברת בירוק. נמדד ולא הונח: OPTIONS בלי מפתח מחזיר 204 עם `access-control-allow-origin: *`,
ואילו POST בלי מפתח מחזיר 401. כלומר ה-CORS עובד ו-JWT עדיין נאכף על הכתיבה עצמה.

**נורמליזציה וזהות, מקצה לקצה ולא ברמת ה-SQL.** H נשלח בטלפון `+972-50-999-8877` ו-I
בטלפון `050-999-8877`; שניהם חזרו עם אותו `contact_id` ועם `phone: "0509998877"`. השם
העברי נכתב ונקרא חזרה כ«ישראל» — לא כפול-קידוד, לא סימני שאלה. ו-I, ששלח `info` בלי מייל,
לא מחק את המייל שנקלט ב-H (ה-upsert הוא `coalesce`).

**מצב טסט אומת בכך שהתור לא זז.** לפני הבדיקה ואחריה: `outbound_queue=8`, `delivery_log=3`,
`rights.catalog=888`. כל תשובה מוצלחת החזירה `queued:false`. שום הודעה לא יצאה החוצה.

**התגלגל אחורה במלואו.** הבדיקה יצרה 4 פניות (שתי הרצות), 118 שורות `case_rights` ואיש
קשר אחד; כולן נמחקו. אחרי: `cases=0, case_rights=0, documents=0, contacts=4` — זהה למצב
שלפני, שנמדד ב-`0/0/0/4`.

## שתי הכרעות שנרשמות כאן כדי שלא יתגלגלו כטעם

1. **דחיית אימות חוזרת ב-200, לא ב-400.** בקשה תקינה שנדחתה לגופה היא תוצאה תקינה, והלקוח
   קורא `ok`/`error` מהגוף בכל מקרה. כך `non-2xx` נשאר סימן יחיד ל«משהו שאינו הטופס».
   זה גם מה שמחזיק ברשת הזו, שכותבת מחדש סטטוסי שגיאה של Supabase ל-400 — לו הדחיות היו
   4xx, הטופס לא היה יכול להבדיל בין «מצב לא קיים» לבין נפילת שער.
2. **התקרה נמדדת בבייטים ולא בתווים.** `cases.raw` שומר את ה-payload המלא, ולכן גוף גדול
   הוא שורה שנשארת במסד. הטופס בעברית וכל תו בו הוא שני בייטים ב-UTF-8; מדידה באורך
   המחרוזת הייתה מכפילה בפועל את התקרה שנרשמה בקוד.

## שני דברים שנמצאו בדרך ולא נבלעו

- **מחיקת איש קשר מייתמת פניות בשקט.** `cases_contact_id_fkey` הוא `ON DELETE SET NULL`,
  ולכן מחיקת השורה מ-`bkalot_auto.contacts` השאירה שתי פניות עם `contact_id=null` במקום
  לסרב. זה נראה כאן רק כי הניקוי נעשה בסדר הזה. לשכבה 2 (ניהול) זה אומר שרשימת פניות
  שמצטרפת ל-contacts ב-JOIN רגיל תשמיט פניות במקום להציג אותן כ«ללא איש קשר».
- **בדיקה שצינרה את הפלט ל-`Out-Null` עדיין שלחה את כל הבקשות.** ההרצה נראתה שקטה
  לחלוטין והשאירה 2 פניות ו-59 שורות זכויות במסד. הן נמצאו רק כי הספירה שאחרי הניקוי
  לא חזרה לבסיס. לקח למדידה: ספירה שלפני ואחרי היא מה שתפס את זה, לא הפלט.
- **מלכודת מדידה בפוסטגרס:** תת-שאילתת `count(*)` באותה פקודה עם ה-`DELETE` רואה את
  התצלום שלפני המחיקה ומדווחת שכלום לא נמחק. הספירה חייבת להיות פקודה נפרדת.
