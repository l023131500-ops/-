# bkalot-clone שכבה 3, לבנה 3 — קריאת גוף המסמך מעל HTTP (#233 סעיף 2)

**מה היה.** הפעימה הקודמת נתנה ל-`bkalot_clone_render` כתובת HTTP ומדדה אותה:
`document_id=7`, 5,223 תווי HTML בשורה במסד. ואז נסגרה עם `#233` פתוח על שני
סעיפים, וסעיף 2 שלו הוא זה: **אין מה להציג גם אחרי הפקה.**
`bkalot_clone_admin_case` מחזירה מטא-דאטה בלבד, במפורש ובכוונה — `0060` שורה 215
כותבת «גוף המסמך אינו נשלח ברשימה». כלומר מסך הניהול יכול להציג «מסמכים (1)»
ולא את המסמך, והגוף שנכתב אין ולו נתיב אחד שקורא אותו בחזרה.

זה הצעד הזה, והוא בדיוק מה ש-#233 ביקש ולא יותר: «פונקציית קריאה אחת לגוף
המסמך מאחורי אותו שער, ורק אז המסך».

| | |
|---|---|
| מיגרציה | `0064` — `public.bkalot_clone_admin_document(jsonb)`, `service_role` בלבד |
| edge | `bkalot-clone-admin` **v3** — נתיב `document`, `ROUTES` משישה לשבעה |
| מדידה | 18 בקשות על הכתובת החיה + 4 קריאות SQL |
| כתיבה | **אין.** הפונקציה קריאה בלבד, `SELECT` יחיד |

## ההכרעות

**0060 שורה 215 נשארת כפי שהיא.** ההחלטה שלא לשלוח גוף ברשימה אינה תקלה שיש
לתקן: פנייה עם ארבעה מסמכים הייתה גוררת ~20KB בכל פתיחת פנייה, והמסך צריך את
הגוף רק כשנלחץ מסמך אחד. לכן **פונקציה נפרדת** ולא הרחבה של `admin_case` —
הרחבה שם הייתה משנה את מה שכבר נמדד ב-25 בדיקות. נמדד ולא הונח: בדיקה 10 קוראת
ל-`/case` על אותה פנייה ומאשרת `has_body=true` לצד `body_html` **שאינו קיים
בתשובה**.

**הארגומנט `jsonb` ולא `bigint`**, בניגוד ל-`admin_case(p_id bigint)`. זה נגזר
ממדידה: `rpc` עם `bigint` ומחרוזת שאינה מספר מפיל את PostgREST על casting,
והרשת כאן כותבת סטטוסי שגיאה מחדש ל-400 — כלומר הכשל הזה **אינו ניתן להבחנה
מנפילת שער**. עם `jsonb` שום ערך אינו מפיל דבר, והבדיקה יושבת במסד פעם אחת
במקום עותק שני שלה בקוד ה-edge. זו אותה הכרעה בדיוק שנעשתה ב-`render`, ולכן
הקוד ב-edge לא מכיל שם שום בדיקה — הבדיקה של `case` למטה בקובץ קיימת אך ורק
משום ששם הארגומנט `bigint`.

**`length(digits)` נבדק לפני ה-cast.** `'9'` כפול 25 הוא ספרות בלבד ועובר כל
regex, ו-`::bigint` עליו זורק `numeric_value_out_of_range` — שגיאת מסד על קלט
שצורתו לגיטימית. מספר שאינו יכול להיות מזהה הוא פשוט מסמך שאינו קיים. בדיקה 16
מדדה את זה, והיא גם חשפה משהו שלא הונח: `9999999999999999999999999` חוזר מהמסד
כ-`"10000000000000000000000000"` — JSON מפרסר אותו כ-float ומאבד דיוק לפני
שהגיע אלינו. 26 ספרות > 18, ולכן `document_not_found` ולא 502.

**הגוף מוחזר כמות שהוא.** ה-escape נעשה בזמן ההפקה (`0063` הכרעה 4) ולא בזמן
הקריאה. סניטציה שנייה כאן הייתה אומרת שאיננו סומכים על הראשונה — ואז המסמך
שנשלח החוצה שונה ממה שהמנהל ראה על המסך. מה שכן נוסף: `html_chars`/`text_chars`,
כדי שמסך שקיבל גוף ריק יידע להבחין בינו לבין גוף שלא הגיע.

## מה נמדד

**הפריסה עצמה.** `POST /nope` מחזיר את רשימת הנתיבים. v2 הכירה שישה; רשימה
שאינה מונה את `document` הייתה אומרת שהפריסה לא נחתה, וכל השאר היה נכשל מהסיבה
הלא נכונה. חזר `["login","session","logout","cases","case","render","document"]`.
`OPTIONS` בלי כותרות → 204 עם `x-admin-token` ב-allow-headers.

**ה-rpc עצמו אינו נגיש עם מפתח ה-anon** (בדיקה 4): `42501 permission denied for
function bkalot_clone_admin_document`. בלי ה-revoke, `SECURITY DEFINER` ב-`public`
היה פותח לכל מחזיק anon את גוף כל מסמך — והגוף מכיל שם מלא, טלפון ומייל של מי
שהשאיר פרטים. השער הוא ה-edge function, ובדיקה 4 היא מה שהופך אותו לשער ולא
לקישוט.

**השער.** בלי `x-admin-token` → 401 `token_required`. טוקן שלא הונפק → 401
`invalid_session`. אותו טוקן אחרי `logout` → 401 — **גם נתיב הקריאה נסגר עם
הסשן**, לא רק הכותב.

**הקריאה עצמה.** הפנייה נוצרה דרך נתיב הקליטה האמיתי ולא בהזרקה למסד
(`case_id=21`, 59 זכויות), רונדרה (`document_id=12`), ואז נקראה:

| | |
|---|---|
| `ok / id / case_id / kind` | `true / 12 / 21 / email` |
| `case_id` תואם את הפנייה שרונדרה | **true** |
| `html_chars` / `text_chars` מסכימים עם `render` | **true / true** |
| אורך מה שהגיע = המספר שדווח | **true** (5,223) |
| `queue_id` / `queued` / `storage_path` | `null` / `false` / `null` |

שתי המדידות האחרונות הן העיקר: `render` ו-`document` הם **שני מפיקים בלתי-תלויים
שמסכימים על אותו מספר**, ו-`body_html.Length == html_chars` שולל קטיעה בדרך.
מפיק שמדווח 5,223 וקורא שמחזיר פחות היה נראה כמו 200 בריא.

**העברית חוזרת נקייה.** הקורא הוא הדבר הראשון שמוסר את הטקסט הזה למסך, וגוף
שחוזר משובש נראה בדיוק כמו 200 מוצלח: שם הפונה נמצא ב-HTML → true, ההערה נמצאת
בטקסט → true. `https://more30.com/bkalot-studio` בגוף → true, `javascript:`
בגוף → **false**.

**שגיאות קורא נשארות ניתנות להבחנה:** בלי `id` ו-`id` שהוא מילה →
`document_id_required`; `id` כמחרוזת ספרות → **מחזיר את המסמך** (`p->>'id'`
מנרמל, ולכן `"12"` ו-`12` הם אותו דבר); `id` שאינו קיים → `document_not_found`;
25 ספרות → `document_not_found`.

## ניקוי

מחיקה בסדר הנכון — מסמכים, זכויות, פניות, ואיש הקשר **אחרון**: `cases_contact_id_fkey`
הוא `ON DELETE SET NULL`, ומחיקה הפוכה הייתה מייתמת את הפנייה בשקט.
נמחקו: 2 מסמכים, 118 שורות `case_rights`, 2 פניות, איש קשר 26 (הריצה השנייה
מיחזרה את אותו איש קשר לפי מייל — upsert, ולא נוצר שני). אחרי: `documents=0`,
`cases=0`, `case_rights=0`, `contacts=4` — בדיוק המצב שלפני.

מה שלא נוקה בכוונה ונרשם כדי שלא ייקרא כשארית: `admin_sessions` עלה מ-3 ל-5 —
שתי שורות audit של שתי כניסות אמיתיות שקרו, ולא נתון שהוזרק. שתיהן מבוטלות,
`admin_sessions_live=0`, ו-`admin_users` עם `failed_attempts>0` או `locked_until`
— **0**: הכניסות נעשו נכון ולא נגעו במונה הנעילה של חשבון-העל.

## מלכודת שנמדדה בסקריפט הבדיקה עצמו

הריצה הראשונה החזירה `413 body_too_large` בשתי בדיקות. זו לא הייתה תקלת מוצר
אלא **התנגשות שמות ב-PowerShell**: שמות משתנים שם אינם תלויי-רישיות, ו-
`$doc = $g.document` דרס את `$DOCID`... כלומר את `$DOC`. שתי הבדיקות שילבו אותו
לתוך הגוף ושלחו אובייקט של 9KB כ-`{"id":...}`. השם שונה ל-`$DOCID`, והוסבר
בהערה בקובץ. אילו זה לא היה נבדק, `413` היה נרשם כממצא על המוצר.

## מה נשאר פתוח
