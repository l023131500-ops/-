# שכפול בקלות שכבה 2 — כתובת ה-HTTP של הניהול (13/08/2026, `bkalot-clone-admin` v1)

שתי הלבנות הקודמות בנו שש פונקציות במסד — שתי קריאה (0060) וארבע כניסה (0061)
— ולכל אחת מהן `EXECUTE` ל-`service_role` בלבד. ה-README של 0061 סיים בשורה
מפורשת: «אין ולו כתובת HTTP אחת ואין מסך — השער קיים ואינו מחובר לכלום». זו
הלבנה שנותנת לו כתובת אחת, ורק אותה: **עדיין אין מסך.**

## מה נפרס

`supabase/functions/bkalot-clone-admin` — `verify_jwt=true`, version 1, ACTIVE.
דקה בכוונה כמו `bkalot-clone-intake`: היא אינה קוראת טבלה ואינה מחליטה דבר על
זהות. מה שכן יושב כאן ואינו יכול לשבת במסד הוא **הרכבת השער** — `admin_session`
רץ לפני `admin_cases`/`admin_case`, ולא במקביל להן.

| נתיב | שער | מה |
|---|---|---|
| `POST /login` | — | `email`+`password` → טוקן אטום + `expires_at` |
| `POST /session` | ✅ | מי מחובר |
| `POST /cases` | ✅ | רשימה מסוננת ומדופדפת + `total` |
| `POST /case` | ✅ | פנייה בודדת + זכויות + מסמכים |
| `POST /logout` | — | ביטול, אידמפוטנטי |

**`bkalot_clone_admin_create` אינה חשופה, בכוונה.** פונקציה שיוצרת משתמש ניהול
ואין לפניה שער היא בדיוק החור שה-`revoke` של 0061 סגר; כתובת HTTP אליה הייתה
פותחת אותו מחדש מכיוון אחר. יצירת מנהל נעשית בקריאת SQL ישירה בלבד.

## הסטייה שנכפתה, ונמדדה ולא הונחה

`BKALOT_METHOD` העתיק מהמקור דפוס נכון: **טוקן אטום בכותרת `Authorization`**
מ-state בזיכרון, בלי `localStorage` ובלי cookies (`schema.ts:166-168`). הדפוס
הזה אינו יכול לעבוד כאן, ולא בגלל בחירה: `verify_jwt=true` גורם ל-gateway של
Supabase לפרסר את `Authorization` כ-JWT, והטוקן שלנו הוא 32 בייט אטומים.

| הבקשה | תוצאה |
|---|---|
| הטוקן ב-`Authorization` — **בדיוק כמו במקור** | **401 `UNAUTHORIZED_INVALID_JWT_FORMAT`** |
| הטוקן ב-`x-admin-token`, `Authorization` = מפתח anon | 200 |

הבקשה הראשונה **אינה מגיעה לקוד הזה בכלל**. שכפול נאמן של הכותרת היה מייצר
מערכת שאינה עונה, ושום קריאה בקוד לא הייתה מגלה למה. מה שנשמר מהמקור הוא מה
שחשוב — טוקן אטום מ-state בזיכרון, בלי `localStorage` ובלי cookies; מה שהשתנה
הוא שם הכותרת בלבד.

ומכאן נגזרת מלכודת שנייה, שנרשמה מראש ולא התממשה: `x-admin-token` חייב להופיע
ב-`access-control-allow-headers`. preflight שאינו מכריז עליו גורם לדפדפן לחסום
את הבקשה האמיתית — ובדיקה משורת פקודה, שאינה שולחת preflight כלל, הייתה עוברת
בירוק. נמדד על OPTIONS בלי שום כותרת: `204`, ו-`allow-headers` מחזיר
`authorization, apikey, content-type, x-admin-token`.

## שתי הכרעות נוספות שנגזרות מהמדידה

**`401` ולא `200` על נפילת שער.** בטופס הציבורי דחיית אימות חוזרת ב-200,
כי «בקשה תקינה שנדחתה לגופה» היא תוצאה תקינה. כאן אין זהות ואין תשובה לתת,
והלקוח צריך להבחין בין «הסשן פג, חזור למסך הכניסה» לבין «הפנייה לא נמצאה».

**`ip` ו-`user_agent` נדרסים בערכים מהבקשה עצמה.** 0061 קורא אותם מה-payload,
ולקוח שהיה יכול לכתוב אותם בעצמו היה הופך את שורת ה-audit לעדות שהוא חיבר.
עדיף בלי מקור מאשר מקור שקרי.

## מלכודת בבדיקה עצמה, שנתפסה רק כי המספר היה 0

הריצה הראשונה דיווחה `rights=0` על פנייה עם 59 זכויות. שתי סיבות נפרדות,
ושתיהן שקטות: (1) `Probe` גם הדפיסה וגם החזירה אובייקט, ולכן `| Out-Null`
בלע את הדוח כולו — 23 בקשות רצו והמסך היה כמעט ריק; (2) `rights` יושב ברמה
העליונה של התשובה ולא תחת `case`, ו-`$one.case.rights.Count` מחזיר 0 — **בדיוק
מה שרשימה ריקה נראית כמוה**. הודעות עברו ל-`[Console]::Out` שאינו הפייפליין,
והספירה נקראת מהמקום שבו היא באמת יושבת.
